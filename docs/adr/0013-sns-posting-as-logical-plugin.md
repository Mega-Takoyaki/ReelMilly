# 0013. SNS投稿機能を論理プラグインとして分離する

- ステータス: 決定
- 決定日: 2026-09-26
- 決定者: プロジェクトオーナー

## コンテキストと課題

[ADR-0007](0007-asset-management-as-core.md)でReelMillyの中核をアセット管理に据えると決定したが、実装上どこまで分離するかは定義していなかった。今回、画像管理アプリを本体として優先実装し、SNS投稿（Fanvue/X）機能を拡張機能・プラグイン的に付加していく方針が示された。

## 検討した選択肢

- 本格的なプラグイン機構（動的ロード、プラグインAPIの外部公開、第三者拡張可能）を実装する
- 論理的なモジュール分割にとどめる（単一プロセス・単一リポジトリ内で、本体とSNS投稿機能をパッケージ/モジュールとして分離するが、動的ロードの仕組みは作らない）

## 決定

論理的なモジュール分割を採用する。

- **本体**: 画像・動画管理（SQLite、ライブラリ管理、フォルダ・タグ、NSFW自動仕分け）
- **SNS投稿モジュール**: Fanvue公式API連携、X Playwright操作、投稿ジョブスケジューリング（drop / x_teaser / x_engagement）

をコード上明確に分離されたモジュール/パッケージとして実装する。動的プラグインロード・プラグインAPIの外部公開は行わない。

本体は、SNS投稿モジュールが存在しなくても単体で成立する（画像管理アプリとして動作する）ように設計する。SNS投稿モジュールは、本体が提供するデータアクセス層（SQLite経由のアセット取得・状態更新）を通じてのみ本体と連携し、本体の内部実装に直接依存しない。

将来的に投稿以外の拡張（別のアセット活用方法）や第三者による拡張が必要になった場合は、本格的なプラグイン機構の導入を再検討する。

## 結果

### 良い影響

- 実装コストを抑えつつ、本体とSNS投稿機能の責務を明確に分離できる
- 将来的に本格的なプラグイン機構へ移行する場合も、モジュール境界が既に明確なため移行コストが低い

### 悪い影響・トレードオフ

- 動的ロードができないため、SNS投稿機能の有効／無効切り替えやバージョン管理は、通常のコードデプロイと同じ手段で行う必要がある
- 「プラグイン」という言葉が連想させる第三者拡張性は、当面提供しない
