# 0005. デプロイ環境（AWS EC2 vs ローカルPC）

- ステータス: 提案中（未決定）
- 決定日: 未定
- 決定者: 未定

## コンテキストと課題

当初、X投稿（[ADR-0002](0002-x-posting-via-playwright.md)、現在は非推奨）はPlaywrightの永続ブラウザプロファイルに依存し、ヘッドレス環境でのセッション維持が弱いという制約があった（CLAUDE_HANDOFF.md 14章）。[ADR-0014](0014-x-official-api-application-first.md)でX投稿を公式API採用（申請ファースト）に転換したことにより、開発者アプリが承認された場合はブラウザ実行環境という制約自体がほぼ解消される。

[ADR-0013](0013-sns-posting-as-logical-plugin.md)で本体（画像管理アプリ）とSNS投稿モジュールを論理的に分離しているため、両者は別々にデプロイ先を検討できる。

## 検討中の選択肢

**本体（画像管理アプリ）のホスティング先**（Playwright採用可否に関わらず独立して検討）
- ローカルPC（Windows）でWebアプリとして常時起動（現時点での基本方針）
- AWS常時稼働（EC2等）

**SNS投稿モジュールの実行環境**（[ADR-0014](0014-x-official-api-application-first.md)の申請結果で分岐）
- 公式APIが承認された場合: ブラウザ不要のREST API呼び出しのみになるため、本体と同じ環境で十分。AWS Lambda等のサーバーレスも選択肢に入る
- Playwrightにフォールバックする場合のみ、以下の判断軸表が意味を持つ

## 判断軸（Playwrightフォールバック時のみ想定。README.md / docs/architecture.md 7章にも記載）

| 観点 | ローカルPC常時稼働 | AWS常時稼働（GUI付き） | AWSオンデマンド起動 |
|---|---|---|---|
| Playwright永続プロファイルの維持 | 容易 | ヘッドレスでは弱い | インスタンス起動のたびに永続化されたプロファイルの復元が必要（EBS/S3同期等の追加実装） |
| 24時間稼働の安定性 | PCの状態に依存 | 安定だがGUI付きはコスト増 | 起動の都度失敗しうる（可用性はオーケストレーション実装次第） |
| 初回Xログイン | そのまま可能 | VNC等の追加構成が必要 | VNC等の追加構成が必要（オンデマンド時のみ） |
| 運用コスト | 電気代のみ | インスタンス費用が継続発生 | 投稿頻度が低い（1日数本）ため、常時稼働よりコストを抑えられる可能性 |
| 秘密情報管理 | `.env`のみで完結 | Secrets Manager等の追加設計が必要 | 同左 |
| 実装複雑度 | 低い | 中程度 | 高い（起動オーケストレーション、プロファイル同期、失敗時のフォールバックが必要） |

## 決定

未定。本体のホスティング先は「基本はローカルWebアプリ」の方向で検討が進んでいるが未確定。SNS投稿モジュールの実行環境は、X開発者アプリの審査結果（[ADR-0014](0014-x-official-api-application-first.md)）を待ってから確定する。公式APIが承認されれば、本体と同じ環境で足りる可能性が高い。
